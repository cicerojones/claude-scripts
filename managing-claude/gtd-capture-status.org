* Goal

  Explore what Claude-enabled automation can add to an existing,
  mature Emacs + org-mode GTD workflow (Mac + Android/Orgzly), without
  replacing any of it — see gtd/CONVENTIONS.org in this repo for the
  schema this converged on.

* Key constraints discovered along the way

  - The Dropbox connector can only *create* new files — no in-place
    edit/overwrite of existing content. This is why the convention is
    "one new file per capture session" (=capture-<Mon><DD>.org=)
    rather than appending to a single running inbox.org.
  - The plain consumer Claude mobile app has no filesystem/shell
    access and acts only through connectors; at the start of this
    session none were enabled. A Dropbox connector became available
    mid-session and is what made the retarget above possible.
  - *Unresolved friction (found 2026-09-06, end of session):* Dropbox
    on macOS can leave files "online-only" — 0 bytes on local disk,
    not actually materialized — until some local app (Finder preview,
    TextEdit, etc.) forces a real download. Emacs can only see/write a
    file once that's happened. So a file the Dropbox connector creates
    in the cloud is not guaranteed to be immediately visible/editable
    from Emacs. This is a macOS/Dropbox client setting (forcing the
    folder to "Local" rather than "online-only" storage), not
    something fixable from an automation session — needs to be set on
    the Mac directly. Left open; next session should check whether
    setting that folder to always-local storage resolves it.

  Noted capabilities/limits for whoever picks this up:
  - Dropbox connector can browse/search/list/read metadata across the
    whole account, and can move/rename/copy/delete after explicit
    per-action confirmation (delete = Dropbox's own trash, not
    permanent).
  - No built-in duplicate-file detector; would need to be approximated
    from listing + metadata (name/size, and content hash *if* the
    connector's metadata actually exposes one — unconfirmed).
  - Given the scale (a decade-plus, multi-thousand-file account), a
    full sweep is a big, many-call job — better scoped as its own
    task, likely starting with one subtree (e.g. just
    Archives-ALL/MOVING-remote) rather than the whole account.
